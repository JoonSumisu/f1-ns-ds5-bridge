# 调研与发现记录

本项目调过的问题里,有几个是**公开资料几乎没有、必须读上游源码或抓包才能得到**的结论。全部记录在此,给复刻/改造的人省时间。按主题组织,不按时间。

## 1. DS5 传感器时间戳的真实单位是 0.33µs(不是文档想当然的 25µs)

Linux 内核 `hid-playstation` 驱动里有一行 `sensor_timestamp / 3` 得到微秒——即 DS5 报文 [28..31] 的计步单位是 **0.33µs**。本项目早期按 25µs 填,偏大 75 倍:镜头控制类只读瞬时角速度的功能无感,但任何按时间戳做姿态融合的功能(Steam 的陀螺仪融合器、MW4 武器控制)都会被错误的 dt 破坏。

**教训(v5.4 事故)**:曾尝试把突发三采样"等间隔化"重排时间戳,实测产生 dt=0/25ms 锯齿(正确应为 ~16.7k counts 一档),Steam 融合器直接爆掉、游戏内左右翻失控。回退为墙钟差值×3 后正常。**结论:时间戳任何语义改动,必须先用探针工具看 dt 直方图,再进游戏。** 探针在本仓库 `tools/ds5_probe.py`。

## 2. 轴向映射:双上游源码交叉验证

把 Switch IMU 轴映射到 DS5 轴,本项目矩阵为 accel/gyro 同号:`(-Y_sw, +Z_sw, -X_sw)`。验证链:

- **SDL2** `SendSensorUpdate` 注释 "shuffled to match PlayStation":`-Y, +Z, -X` —— 与本项目完全一致;且 SDL `hidapi_ps5.c` 对真 DS5 不做任何翻转 → 我们的字节 == 真 DS5 原始值。
- **JoyShockLibrary**(JSL):DS5/DS4 原始直通(16.384 c/dps、8192 c/g);Switch accel 映射 `-sw1, +sw2, -sw0` —— 与本项目完全一致。JSL 的 gyro Z=+swg0 与我们相反,但该值在 JSL 里是死代码(`gyroZ = 0.f`),从未被修过。物理判据:同芯片陀螺仪必与加速度计共享轴系符号 → SDL/本项目正确,JSL 的 Z 是未修复 bug。

Roll 轴历史上是"没人消费"的轴,MW4 武器控制是第一个主流消费者——这就是为什么这个轴映射错误直到 2026 年才暴露。

## 3. 陀螺仪刻度:名义 16.384 c/dps 是错的,893(mdps→counts)才对齐手感

Switch 生态全线使用 STMicro ×1.15 修正后的**有效刻度**(名义 16.384 ÷ 1.15 ≈ 14.28 c/dps):

- Linux `hid-nintendo`:`JC_IMU_GYRO_RES_PER_DPS = 14247`
- SDL `hidapi_switch.c`:`SWITCH_GYRO_SCALE = 14.2842`
- Bluepad32 同源

本项目定案:counts = mdps / 893(有效 14.288 c/dps,与 SDL 差 0.03%)。用名义 16.384 会低灵敏 14.7%,实测"手感不对"。基准是什么?**同一只手柄 NS 档直连 PC 的手感**——用户盲测校准出来的锚点。(桌面定角积分的物理真值 ~15.5 c/dps,本常数比物理高 ~9%,刻意为之:对齐 NS 直连而非物理。)

## 4. MW4 "武器控制"体感模式的真实语义(以及为什么它"没出来")

- 语义:准星在屏幕中心附近的**有界窗口内微调**,不转视角(Wii 光枪式精瞄),设计上与"镜头控制"(经典陀螺仪转视角)叠加使用;主要在 ADS 下生效。
- 毡上的"没反应/反了":各行为(Behavior)默认 Off 是"功能没出来"的常见原因;**真 Switch 2 手柄在 beta 固件上有同款反转 bug**(社区实锤:PS5 正常、Switch 2 "definitely inverted"),是游戏侧 bug,与本转译无关。
- 本项目 roll 轴已按第 2 节验证为正确字节序,真 DS5 对比无差异。

## 5. 振动"常震"的两个根因(都靠遥测抓包定案)

1. **0/0 特判缺失**:Bluepad32 的 Switch rumble 编码幅值写死 500,**任何** `R0,0` 停止命令都会触发一次满幅震动。空闲保活连发 R0,0 = 持续嗡震。解法:停止命令一个字节都不发,靠 TX 侧 250ms 定时自动停。
2. **Steam 常驻帧污染**:Steam 连接期间持续发 0x02 输出报告(音量/灯条),这些帧的振动字节非零但**使能位没置**。旧"峰值代理"把音量字节当振动 → 一直在震。解法:振动字节必须由 b[1].bit0 / b[39].bit2 使能位门控,另加地板值(幅值 <70 归零,滤掉游戏低强度质感振动在手柄上的嗡震表现)。

另:振动转发后 Bluepad32 侧有跨任务坑——非 btstack 任务直接调其 API 会触发 `xQueueSemaphoreTake` 断言崩溃,必须标志位 + 回调内代发(延迟最多 ~8ms)。以及解析 `R<w>,<s>` 不能用 sscanf:newlib 深栈在 2KB 任务栈上溢出,踩坏 UART 驱动,手写解析器解决。

## 6. 采样率上限 ~180Hz 是手柄侧硬限制

F1 的 NS 档经典蓝牙协议:IMU 以 60Hz×3 采样打包上报,**上限 ~180Hz,手柄固件层决定,桥接固件无法提高**。USB FS 中断端点 1ms 轮询不是瓶颈。优化方向只剩延迟:UART 921600(突发 4ms→2ms)、通知唤醒(样本到位即刻发,均省 ~1-2ms)。实测 DS5 报文率 ~175Hz。

## 7. 固件样貌仿真:全零 fw 版本会被 Steam 判"未知设备"

DS5 feature 报告 0x20(固件信息)全零时,Steam 将设备判为未知 → 陀螺仪不做校准直读(实测 16 倍过灵敏)。回填真实样貌(hardware/fw/update),且 update 字段取当前最新线 0x0630:SDL 以它为 `firmware_version`,≥0x0224 才走增强震动路径(0x02 报告的 EnableBits3 语义),转发已兼容。COD 的原生体感"半支持"判定疑与过低 fw 版本有关。

## 8. 电池编码

DS5 [53] 字节:低 4 位 level 0-10(百分比 = level×10+5),0x0C="不报电量",高 4 位充电态(0 放电/1 充电/2 充满)。Bluepad32 侧语义:0=未知、1=空、64/128/192=三档、255=满。注意 SDL 对 Sony 原厂 VID **无条件**开启电量上报(第三方才查 capabilities2),所以这个字段必须填对。[54] 填 0x08(USB 连接态)。

## 9. 供电事故分析:两电脑共地环路击穿 VBUS 保护二极管

事故:装置经杜邦线共地横跨两台电脑,热插拔瞬间地电位差泄放,S3 原生口 VBUS 路径上的 SS54 肖特基(丝印 SS54,常见于双 Type-C 板的 OR 供电二极管)击穿鼓包。

诊断要点(复盘花了整晚,写下来给人抄):

- 症状:某 USB 口插上完全无反应(无枚举)。
- 关键判据:**换另一个口供电,数据口插主机**——若枚举成功,说明只是 VBUS 二极管烧断,数据通道完好,两口分工(一口供电一口数据)可救活。
- 双 Type-C 板"5V 排针"常见陷阱:该脚只连原生口 VBUS 经 OR 二极管,用另一口供电时量到 ~2.9V 是高内阻万用表的**幽灵电压**,不代表 5V 网有电。要取真 5V,焊到 AMS1117 输入脚(任何口供电都必有 ~4.7-5V)。
- 预防铁律:整套装置任何时刻只连**一台电脑**(详见 docs/wiring.md)。

## 10. NS 档扳机只有数字量

NS 协议里 brake/throttle 恒为 0 或满幅,没有模拟行程。DS5 报文的 l2/r2 若恒 0,游戏里扳机无效。解法:数字按下合成满行程 255。
